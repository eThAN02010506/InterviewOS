# InterviewOS 产品需求文档

## 1. 产品目标

InterviewOS 是一个面向候选人和面试官的本地优先面试智能系统。系统在面试前理解
候选人、岗位、公司和面试官，在面试中辅助提问和记录证据，在面试后生成可追溯的
评价与改进建议。

最终目标是让 AI 接管面试流程中的低价值操作：资料整理、事实校验、问题准备、追问
建议、转写记录、证据归档、评分汇总和报告生成。AI 不接管候选人的真实回答，也不
绕过面试官对提问、事实修正、证据确认和录用建议的最终判断。

当前阶段的重点是实现 **面试官实时 Copilot**：在获得明确授权后监听面试对话，持续
整理候选人的回答和能力信号，并在不打断交流的前提下为面试官准备下一道问题。

本文档是实现过程中的产品真实来源之一。每次完成一批重要功能时，应同步更新本文件
和 `README.md`，再提交包含充分说明的 commit。文档需要记录：当前已完成能力、下一步
顺序、已知限制、隐私/安全边界，以及真实测试结论。

## 1.1 产品原则

- 本地优先：简历、转写、密钥和调试信息默认保留在本机或用户明确配置的局域网服务中。
- 证据优先：报告、评分和招聘建议必须绑定可追溯证据；证据不足时系统应说明不足，而不是编造结论。
- 人类确认：实体纠错、简历争议项、公开搜索推断和最终招聘判断必须保留用户确认流程。
- 现场可用：面试中 UI 要快、安静、可扫读，不能因为 AI 建议打断面试节奏。
- 可观测但脱敏：Debug Console 应解释耗时、重试和降级路径，但不能泄漏 API Key、简历隐私或完整逐字稿。

## 2. 用户与场景

### 2.1 面试官

- 面试前查看结构化面试计划、能力维度和建议问题。
- 面试中查看实时转写、已覆盖信号、待验证信号和下一问题建议。
- 面试官始终决定是否采用、修改、跳过或延后 AI 建议。
- 面试后审阅记录、纠正说话人或转写错误，再生成评价报告。

### 2.2 候选人

- 面试前获得岗位和面试官分析、准备策略及模拟面试。
- 仅在知情和同意的情况下参与被录音或转写的真实面试。
- 面试记录与招聘判断不得混入未确认的简历事实或公开搜索推测。

## 3. 当前实现状态

### 3.1 已完成

- 候选人端和面试官端分离的基础 UI。
- PDF 与 Word `.docx` 简历上传、解析、警告和人工审阅项识别；PDF 提取已从 pypdf 升级为 pdfplumber，保留结构换行与表格行序，减少列对齐填充噪声对证据提取的污染；docx 表格按行提取避免多行表格坍缩；竖排日期范围自动合并，裸英文公司名可识别。
- 可选 AI 结构化增强：上传时勾选"AI 结构化增强"（或 `structure=llm`），由可配置的本地多模态模型（设置 → resume_llm，如 Qwen3-Omni 8004）把简历文本解析成语义板块（教育/工作/研究/领导力/奖项/技能），修复规则匹配的盲区（含 university 的研究描述不再误判为教育、奖项不再误判为工作）。实测 Mingyuan 简历：规则版 8 条含多处误判，LLM 版 15 条全部分类正确；LLM 不可用时自动回退规则结果。默认可复用主 LLM，但用户首次单独配置 `resume_llm` 时必须拆分独立客户端，不得连带修改主推理模型。
- 候选人、岗位、公司、面试官分析，以及候选人准备策略和企业面试设计。
- Tavily、SearXNG、Brave 搜索 Provider 接入，运行时配置和本地持久化。单次更新必须在进程内串行并具有事务性：任一 Provider 校验或本地保存失败时，搜索、主 LLM、ASR、实时音频和简历 LLM 都恢复到请求前状态，不得出现“返回失败但部分已生效”。
- 实体确认机制：例如搜索到“芯视界”时，可以保留“芯世界”为用户输入，等待用户确认是否更正；用户也可以手动编辑确认后的 canonical name。
- 搜索事实卡片：结论绑定来源，并区分已验证、推测、冲突、已确认或已排除；UI 按冲突、公司、面试官、技术方向和公开观点分组展示，展示来源数量、最佳来源质量、抓取时间、缓存命中状态、筛选原因和生成时间，并支持确认使用、排除和恢复待审。
- 简历真实性审阅闭环：已支持本人确认、修改并确认、要求材料、忽略和恢复待核验，并可让后续 Agent 使用确认后的候选人事实上下文。UI 必须明示“本人确认不等于外部真实性验证”，不得把简历自述显示为已核验事实。
- JD 完整性审阅闭环：标题型或不完整 JD 会区分明确要求与 AI 推测；获得公开检索授权后，只有职位名称时会先检索并筛选相关公开 JD，再将带来源的待确认摘要供岗位分析和出题使用。未授权或无可靠来源时明确降级为通用问题。推测要求可确认、编辑为明确要求或删除。
- Mock 面试闭环：候选人回答、追问、评分、证据记录、最终报告和改进建议。
- Debug Console：展示 Agent 生命周期、耗时、故障、设置状态和连接探针，并进行密钥脱敏。
- Live Interview Copilot 的轮次式 MVP：面试官明确确认后，支持手动文本或单轮录音转写，生成下一问题建议，并允许采用、编辑或跳过。
- Live evidence 审阅闭环：转写片段可在归档前修改说话人与文本，候选人回答可确认为 `live_interview` 证据，批量审阅队列会提示证据数量和胜任力覆盖是否达到招聘评价门槛；能力地图会按岗位能力给出证据数量、最强信号、优先级、缺口原因和下一问题样例；蓝图问题使用图会区分待问、已建议和已采用问题；Live 动作卡会按说话人审阅、回答边界合并、证据确认、问题建议处理、证据缺口补齐和最终评价就绪的顺序给出面试官下一步，并提供可点击 CTA：安全动作可直接触发，需要判断的动作会定位并高亮对应审阅区域；已归档 live 证据可撤销，转写片段保留以便修正后重新确认；多个候选人片段可合并为一个回答再评分；连续未归档候选人片段可生成保守的回答边界建议，并展示关联问题、连续片段数、回答长度、结束语信号和 ASR 参与等可解释置信度因素，由面试官确认后合并入证据；已归档记录可在保留证据链的前提下重评。
- 静音切块连续监听 MVP：浏览器用 Web Audio VAD 持续录音，停顿约 0.6 秒就把当前整段发言（utterance）定稿，作为一个自包含音频块顺序上传到现有 HTTP ASR（每个 utterance 独立 MediaRecorder 会话，保证每个上传都能干净解码）；说话时显示"正在听取 (Xs)"指示器；`asr_text` 模式默认把分段标记为 `unknown` 说话人，必须审阅后才能形成证据；`audio_direct` 模式每段以 `mode=dialogue` 上传，由 8004 自动分说话人；Live 状态会丢弃精确重复片段，并把旧稳定转写压缩为滚动摘要，供下一问题规划使用。
- 实时辅助性能优化：证据确认后立即返回，评分（coach_agent）改为后台异步执行，不再阻塞下一问题建议；确认那一刻即在 `evidence` 中落一条占位证据（`scoring_status=scoring`），覆盖引导与行动卡的证据统计立即准确，评分完成后回填置信度并标记 `scored`。下一问题建议在证据确认后自动触发（无待处理建议时），前端 live 视图按 3 秒轮询刷新评分状态与建议卡，去掉"确认证据后再手动点击生成下一问题"的中间等待。
- 真实 UI 使用加固：`resume_text` 在自动/工作流请求中改为可空，面试官只填 JD 不填简历也能启动；`think_structured` 对非法输出轻量重试一次再兜底，避免无兜底 Agent 因模型输出漂移导致整个工作流 502；企业面试设计在模型返回空轮次时用 JD 能力生成确定性通用蓝图，无简历场景不再失败。以上均通过真实 8001 模型实测验证。
- 面试官端真实测试：已通过本地 API 跑通企业面试设计、live 记录、证据归档和最终评价；证据不足与证据充分两条路径均有回归测试。
- Live 动作卡真实 HTTP 验收：`scripts/e2e_live_action_card.py` 已跑通开始会话、边界合并、证据确认、下一问题自动规划与采用、结束会话和招聘评价；2026-08-05 本地 8001 模型实测总耗时 86.307 秒，其中动作卡/下一问题 24.631 秒、最终评价 40.886 秒（上一轮 2026-08-02 为 113.823 / 33.033 / 51.191，差异来自证据评分异步化与规划器上下文瘦身）。
- ASR/LLM 局域网联调：
  - 文本推理模型：`http://192.168.1.97:8001`，`gpt-oss-20b`。
  - 默认 ASR：`http://192.168.1.97:8007`，Qwen3-ASR-1.7B，多句中文转写约 5.1s、文本干净；`http://192.168.1.97:8003`（MiMo-V2.5-ASR）已验证可作备选。
  - 备选 ASR：`http://192.168.1.8:9001`，接口可用且更快，但实测同一多句音频只返回首句，因此暂不作为默认证据来源。

- 全页面 UI 实测：浏览器驱动走通候选人端（面试准备/模拟面试/改进报告）与面试官端（面试设计/实时辅助/候选人评估）全部页面，控制台零 JS 错误；JD 推测要求确认与简历 claim 确认均真实回写服务端。实体确认弹窗与事实卡 UI 因需公开搜索命中才触发，本轮以 API 单测覆盖未走 UI 实测。
- 真实使用加固：简历可空（只填 JD 不再 422）、结构化输出失败轻量重试一次、面试设计与策略 Agent 在模型输出为空时生成确定性兜底，避免整个工作流失败。
- 实时音频可切换：新增 `live_audio` 配置（设置页"实时音频处理"面板），`asr_text`（ASR+文本模型）与 `audio_direct`（音频直连全模态模型，如 Qwen3-Omni 8004）两种模式并存；支持自定义显示名、地址/模型、能力探测（真实音频样本验证端点可返回可用问题）。直连模式不生成转写段，建议直接注入审阅队列。直连上下文按实际场景设计为**聚焦现场 + 优先级分级**：只携带岗位/已覆盖能力（锚点永保）、最近稳定对话、最近 live 证据，排除蓝图/摘要/覆盖引导等推进型信息以保持低 prefill；超限时从低优先级块开始丢弃而非尾部截断。实测带 7 轮蓝图会话中，聚焦直连约 3.5s 返回基于音频+岗位能力的追问（全量上下文版约 8.9s，ASR+20B 文本路径约 32s）。
- 建议流式：SSE 端点 `POST /api/live-interviews/{id}/suggestions/stream` 使用 HTTPX 真实流式响应（不先缓冲完整 completion），LLM 建议逐 token 推送；前端"流式生成"请求携带当前账号 bearer token，并按 JSON 编码解析 `append/replace` SSE 事件，避免模型换行破坏分帧；上游中途断线时用安全问题替换半截输出，内部错误不得显示或持久化；若生成期间面试已暂停或结束，迟到的建议不得写回会话。转写仍按分段上传（8007 无流式接口）；单测使用门控异步 byte stream 验证第一个 token 在响应结束前到达，已有 8001 真实模型的整体耗时记录保留作为环境基线。
- 自动说话人分离（audio_direct）：8007 ASR 的 diarize 实测无效（返回无说话人标签），改用 8004 全模态直连——"对话模式"录音（不选说话人）→ 8004 逐句标注说话人 → 合并连续同说话人为一段转录段（候选人长回答=1段可整体确认证据）。实测真实双人中文对话 4 轮全部正确区分；分错保留手动修正。连续监听同样复用该路径：每个静音定稿的 utterance 以 `mode=dialogue` 上传，8004 自动标注说话人。
- 本地多账号与数据隔离：注册/登录（PBKDF2 密码哈希 + 不透明 bearer token），`interview_sessions.owner_id` 按账号隔离，跨账号访问返回 404；业务、设置和 localhost Debug API 均强制登录，Debug 事件在写入时绑定 owner（包括无 session_id 的搜索/后台事件）并按当前账号过滤，仅显式测试/开发配置可关闭；升级前的 sentinel `local` 会话由第一个真实注册账号原子接管，`local` 保留为迁移用户名且禁止注册；更换简历时必须清空上一份简历的确认项和雇主研究结果。
- 全场录音（默认保存 + 知情同意）：同意后独立录音器捕获整场会话，结束时上传存为 `data/recordings/{session_id}.wav`（每会话一文件、仅本账号可见），可从 live 面板下载；隐私默认从"不保存原始音频"反转为"同意后默认保存"。
- 文字记录导出：`GET /api/interviews/sessions/{id}/transcript` 返回完整文字记录（转写段/建议/证据/摘要），live 面板"导出转写文本"按钮下载。
- 候选人上下文与过往雇主调研：一旦上传简历已产生审阅 claim，策略/企业设计/模拟面试只读取 confirmed/modified 事实，未确认、忽略、争议或要求材料的内容不进生成上下文；直接粘贴且尚无审阅记录的简历可作为"未核验候选人自述"用于准备，不得作为评价证据。过往雇主公开搜索在有审阅记录时只选取已确认 claim 中的公司名，并继续受公开搜索同意门槛约束。
- 无限模拟面试与参考回答要点：模拟面试**不再自动结束**（只有"结束面试"手动结束），题目池 = 策略 likely_questions + 岗位能力模板，缓存 3 题、答到不足 3 题时后台补 2 题（结合简历与已答内容）；题池真正耗尽时先同步插入唯一的本地兜底题，避免慢模型、重复补题或进程重启使面试无题可答；每道题的 `answer_framework` 参考要点由模型按题生成，LLM 未配置、失败或返回不完整时使用确定性候选人上下文兜底；支持自由导航："上一题"/"下一题"（可跳过未答题）/"重新来"（按回答 ID 精确替换，追问重答不覆盖主问题；主问题重答会删除由旧主回答派生的追问及证据）/"结束面试"。已回答的旧题必须显式 `retry`，前后端共同防止重复 response/evidence；最终评价经过可恢复的 `evaluating` 状态，失败时保留回答并回到 active 允许重试；进程恢复时会清理补题标志，并把中断的 evaluating 恢复为可重试 active。
- 模拟面试语音闭环：新问题可由设置页配置的 8002/Qwen3-TTS 自动或手动朗读；录音期间以 2.5 秒有界累积快照显示临时转写，草稿不持久化也不进证据；停止后可立即回放，提交回答时将原始录音按回答 ID 绑定到本地会话，刷新或回看旧题仍可通过鉴权接口播放；由 8004 全模态模型分析语速、停顿、填充词、音量稳定、语调变化和清晰度。超时/不可用时在 25 秒内降级为转写文本和音频时长指标。该反馈仅用于表达训练，不评价口音/性格/人口属性，不进入胜任力证据或录用判断。
- 口语回答语义分析：保留原始转写作为证据，另行生成去除非语义填充词的清洗稿；识别行为案例/情景/动机/方法论等回答类型，以原文片段提取语义步骤，并对真实案例、方法、执行动作、个人决策和结果验证做覆盖检查。二次校准只能下调缺少证据支持的模型分数，必须展示每条调整理由。
- 四维行为锚定反馈：每道回答按“岗位相关证据 / 决策与专业深度 / 表达结构 / 结果与复盘”四项等权评分。每一项都展示从候选人原回答中可观察的依据、行为水平和一条具体下一步，并按最弱维度生成优先改进项。

- 现场转写证据增强：确认后撤销、多片段合并为一个回答、保留证据链重评、连续候选人片段的保守回答边界建议、基础可解释边界置信度、精确重复片段丢弃、滚动摘要上下文、能力覆盖引导、蓝图问题使用图和带可操作 CTA 的服务端 Live 动作卡已完成；后续仍需增强语义级/流式级边界判断与置信度校准。
- 连续监听增强：静音切块定稿已完成；后续仍需 WebSocket/流式转写、更强回答边界检测、断线恢复和协议级重复消息去重（说话人分离已由 audio_direct 连续监听交付）。
- 长面试性能和可靠性：证据评分已后台异步化、下一问题建议自动触发，关键路径只保留一次规划调用；规划器上下文已瘦身（只带未用蓝图题+最近关联题、滚动摘要截短到 1500、只带 live 证据、`max_tokens=512`），坏输出直接确定性兜底不再二次预填充，代表蓝图上规划上下文约降 33%；尚未达到 5 秒下一问题目标（受本地模型速度影响），仍需 60-90 分钟压力测试、Token/成本统计、缓存、并发和模型延迟优化。

## 4. 实时面试 Copilot 核心流程

1. 面试官选择候选人会话和面试轮次。
2. UI 显示麦克风、转写和数据用途说明，由面试官确认候选人已知情。
3. 面试官点击“开始监听”，浏览器采集音频并分片发送到本地服务。
4. ASR 返回带时间戳的增量转写；用户可暂停、恢复和手动修正文本。
5. 系统区分面试官问题与候选人回答。无法可靠判断时标记为“待确认”，不得直接形成证据。
6. 候选人回答结束后，系统更新能力覆盖和缺失信号，并准备下一问题建议。
7. 面试官选择“采用”“编辑后采用”“跳过”或自行提问。
8. 面试结束后，面试官审阅记录并确认，系统再运行最终招聘评价。

## 5. 功能需求

### FR-1 实时会话控制

- 支持开始、暂停、恢复和结束实时面试。
- 同一面试会话只允许一个活动监听流，重复连接不得产生重复证据。
- 浏览器断线后可以从最后确认的转写片段恢复。
- UI 必须持续显示监听状态，不允许后台静默录音。

### FR-2 增量转写

- 阶段一允许浏览器以静音切块（Web Audio VAD）把整段发言定稿后顺序上传到现有 HTTP ASR
  文件转写接口，作为连续监听的最小可用版本。该版本必须清晰标注“分段转写”，不伪装成
  真正的实时流式 ASR。
- 阶段二浏览器以短音频块发送数据，服务端维护长生命周期 ASR 实例，禁止每块重新加载模型。
- ASR 通过可配置的局域网 Provider 接入。已验证的默认地址为
  `http://192.168.1.97:8007`（Qwen3-ASR-1.7B），8003 MiMo-V2.5-ASR 作为已验证备选；地址不得硬编码到业务逻辑，用户可以在设置界面修改地址、
  模型名、请求超时和鉴权信息。
- 接入适配器同时覆盖健康检查、批量转写和流式转写能力探测。若服务只支持文件上传，
  后端应合并短音频块后异步提交，不让该协议差异进入前端代码。
- 转写片段包含 ID、开始时间、结束时间、文本、稳定状态和说话人角色。
- 临时文本可被后续 ASR 修订；只有稳定片段可以进入问题规划上下文。
- 当前 HTTP ASR 不提供原生流式协议时，浏览器可有界地上传当前发言的累积快照作为预览。服务端预览端点不得改变会话状态，前端必须标记“实时转写草稿·尚未进入证据”，并以停止后最终整段转写覆盖草稿。
- 支持面试官手动粘贴文本，便于无麦克风环境测试同一数据流。
- 当前 HTTP 轮次式录音上传已经完成；按静音分段的整句上传应复用该 API 边界，后续真正流式
  监听不得改变前端对 ASR Provider 的抽象边界。
- 在没有可靠 diarization 之前，连续分段转写默认说话人为“待确认/unknown”，用户修正
  说话人和文本后才能进入证据确认流程。

### FR-3 说话人和轮次识别

- 最低可用版本允许用户手动指定“面试官/候选人”。
- 自动说话人识别属于增强能力，低置信度结果必须请求确认。
- 一个问答轮次由面试官问题、候选人回答和可选追问组成。
- 寒暄、隐私信息和未完成语句不进入能力评价。

### FR-4 下一问题规划

系统在候选人完成回答后生成结构化建议，至少包含：

- `suggested_question`：建议问题；
- `question_type`：追问、下一主问题或澄清；
- `competency`：要验证的岗位能力；
- `rationale`：为什么现在问；
- `evidence_gap`：当前缺失的证据；
- `expected_signals`：回答中应观察的信号；
- `source_question_id`：来源于哪道计划问题；
- `confidence`：建议可信度；
- `alternatives`：最多两个备选问题。

规划优先级为：

1. 当前回答暴露了关键缺口时，提出一次证据型追问；
2. 当前能力证据已经充分时，推进到尚未覆盖的岗位能力；
3. 回答或转写不完整时，只建议澄清，不进行负面评价；
4. 所有核心能力已覆盖时，建议结束该轮或让候选人提问。

AI 不得连续生成无限追问。默认每道主问题最多两次追问，面试官可以调整上限。

### FR-5 实时面试官工作台

页面采用三栏或主次双栏布局：

- 当前对话：实时转写、说话人、时间戳和修正入口；
- 面试地图：计划问题、能力覆盖、已确认信号和待验证项；
- Copilot：下一问题、提问理由、预期信号和备选问题。

关键操作必须在单击内完成：采用、编辑、跳过、固定问题、标记已问、暂停 AI 建议。
建议卡不得遮挡对话，也不应自动朗读或自动向候选人提问。
连续监听模式必须始终显示录音状态、待上传片段数、正在转写状态和降级提示；说话过程中
需显示"正在听取 (Xs)"指示器，停顿约 0.6 秒即结束当前发言；停止监听
后仍需完成队列内已录到片段的处理，失败片段不得阻塞用户手动录入。

### FR-6 证据与评价

- 实时片段本身不是招聘证据；只有完整候选人回答经确认或稳定处理后才能形成证据。
- 每条证据绑定问答轮次、能力维度、原始转写片段和来源 `live_interview`。
- AI 推断与候选人原话必须分开存储和展示。
- 说话人未确认、转写不稳定或上下文不足时，证据状态为“待确认”。
- 最终评价继续遵守现有证据门槛和来源约束。
- 单题评分使用四个等权维度：岗位相关证据、决策与专业深度、表达结构、结果与复盘。每项 0–1，均值是该题 Evidence 的置信度；若未有经验证的岗位特定权重依据，不得隐式改变维度权重。
- 每个维度必须返回行为水平（表现突出/达到要求/证据有限/需要补强）、可观察的原回答依据和一条可执行修改。未在回答中观察到的行为不得作为评分依据。
- 模型返回的 `observed_signals` 只能作为辅导提示，不得直接成为持久化正向 Evidence；Evidence 的 signal 必须引用候选人原回答，且在人工复核前 polarity 保持 neutral。
- 最终招聘评价按胜任力聚合已持久化 Evidence，正向信号按置信度计分，人工标记的负向证据只能提供有界负向贡献，不得因为低置信度反向提高总分。存在未复核规则分、未完成后台评分或证据不足时，强制返回“证据不足”。

### FR-7 调试与运行指标

Debug Console 增加以下脱敏事件：

- 音频块数量、处理延迟和全场录音大小，不记录原始音频内容；
- ASR 实时系数、转写失败和断线恢复；
- 问题规划触发原因、模型耗时、重试和降级路径；
- 结构化输出失败的字段位置、校验类型、尝试次数、响应字符数和 JSON Schema 模式；不得记录模型原文、简历或回答内容；
- 建议被采用、编辑或跳过的结果；
- 上下文字符数、Token 和成本估算；普通与流式文本模型请求都必须纳入累计，流式 Provider 不返回 usage 时对已接受的输入和完整输出做本地估算。

### FR-8 实体确认

- 当搜索结果显示用户输入实体可能是别名、错字或同名混淆时，系统必须创建确认项。
- UI 应明确显示“是否将 A 更正为 B”，并展示支持来源。
- 用户确认前，系统不得把候选实体改写为 canonical identity。
- 用户可以接受、更正为其他名称、拒绝或暂缓；每个决定都应记录到会话状态。

### FR-9 JD 完整性校验

- 系统应判断 JD 是否只有标题、职责不足、要求不足或缺少团队背景。
- 上下文不足时，问题生成仍可继续，但必须标记为“通用问题”或“AI 推测”。
- UI 应提示补充岗位职责、任职要求、团队规模、技术栈、业务目标和面试轮次目标。
- 面试计划中必须区分用户明确给出的要求和 AI 根据岗位标题推测的要求。
- 只有岗位名称且用户已授权公开检索时，系统必须在出题前检索“职位 + 公司 + 岗位职责 + 任职要求”，按职位关联性筛选来源，并将摘要和 URL 绑定到 JD 审阅。
- 公开 JD 不得改写用户的原始输入，不得标记为目标公司的明确要求；在用户确认前一律是 `inferred`。
- 即使后续 Agent 或工作流失败，也必须恢复并持久化用户原始 JD 与公开来源状态，禁止把内部拼接的搜索 Prompt 暴露为用户输入。

### FR-10 事实卡片

- 搜索结论应按公司、面试官、技术方向、公开观点、争议信息分组。
- 每条事实卡包含结论、状态、来源 URL、来源数量、最佳来源质量、真实抓取时间、缓存命中状态、筛选原因、事实卡生成时间和可信度说明。
- 冲突信息不得被合并成单一结论；需要在 UI 中并列展示并请求用户判断。
- 事实卡只能用于增强上下文，不能替代候选人的面试表现证据。

### FR-11 简历真实性审阅

- 每个简历待确认项支持确认、修改、要求材料、忽略。
- 修改后的事实应保留原文和修订后的结构化值。
- “要求材料”项应进入候选人准备建议和面试官核验清单。
- 后续 Agent 只能读取确认、修改后确认或明确允许使用的事实。

### FR-12 候选人语音练习与表达辅导

- 模拟面试当前问题支持自动朗读和手动重放；TTS 地址、模型、路径、声音描述和密钥可在 UI 调整并安全持久化。
- TTS API 只允许合成当前账号/会话的当前面试问题，不接受任意客户端文本。
- 已回答问题的朗读必须绑定持久化回答 ID，准确区分主问题与追问；切题或切换会话时必须取消旧请求并校验迟到响应的会话/问题身份。
- 候选人停止录音后必须能立即回放本次原始录音；录音先以不可猜测 ID 暂存，提交回答后绑定到回答记录，校验账号和会话归属后才允许刷新后回放。重答替换时删除旧录音，未提交暂存录音 24 小时后可清理。
- 录音、临时转写、回放和表达反馈必须限定在录音开始时的会话；切换候选人会话时必须停止媒体轨、撤销对象 URL、清空旧反馈，迟到响应不得写入新会话 UI。
- 音频分析只评价可改变的表达特征：语速、停顿、填充词、音量稳定、语调变化和清晰度。禁止评价口音、性格、情绪健康、年龄、性别、族裔等个人属性。
- 服务端必须检查全模态模型输出；一旦包含禁止推断，整份模型反馈降级为确定性表达建议，不能仅依赖 Prompt 约束。
- 语音表达反馈只是候选人辅导数据，不持久化为 Evidence，不影响四维能力分数或录用建议。
- 转写文本的口语清洗、回答类型、语义步骤、要求覆盖和证据一致性校准必须随回答持久化；清洗稿不得覆盖原始转写，校准不得上调模型分数。

## 6. 非功能需求

### 6.1 延迟

- 稳定转写应在说话后 2 秒内出现，目标值为 1 秒内。
- 回答结束后的第一张建议卡应在 5 秒内出现。
- UI 更新不得等待最终评价 Agent；实时辅助和面试后评价使用不同任务队列。

### 6.2 上下文与性能

- 不把整场逐字稿反复发送给模型。
- 模型上下文由最近若干轮对话、滚动摘要、岗位能力地图和已确认信号组成。
- 增量处理复杂度应接近 O(n)，其中 n 为转写片段数量。
- 每场面试设置最大时长、片段数和上下文 Token 上限。

### 6.3 可用性与降级

- LLM 不可用时继续转写和手动记录问题。
- ASR 不可用时允许粘贴文本或手动录入问答。
- ASR 健康检查失败时禁止显示“正在监听”，UI 应明确显示“音频采集中但转写服务不可用”
  或“未开始采集”，避免给用户错误的隐私和运行状态暗示。
- 网络或浏览器断开时保留已确认片段，恢复后不得重复评分。
- 模型返回无效结构时展示基于面试计划的确定性备选问题。
- 回答评分模型连续返回无效结构时，必须按回答细节长度、具体行动、结构标记、结果标记和已核验指标生成可解释的确定性降级评分，并显式标注人工复核；不得给所有失败回答固定相同分数。
- 主问题或证据追问提交后，结果页的问题文本必须来自该评分记录实际绑定的 `question`；只有用户明确点击下一题后才能切换，禁止把追问评分显示在主问题旁边。
- 候选人端个人改进报告不得出现“推荐录用/不录用”等招聘结论，也不得使用“要求候选人”式面试官指令；摘要只能讨论准备度和证据缺口，行动计划必须转换为候选人可直接执行的练习。招聘建议只在面试官端展示。
- 面试官端招聘建议的胜任力分数、置信度、支持信号、缺口、摘要和风险必须从持久化 `Evidence` 确定性重建；最终评估与反馈阶段不得调用 LLM。`strong_hire` 至少要求总分 0.85 且聚合置信度 0.75，禁止弱证据因模型自由文本升级为录用建议。
- 回答评分模型只允许返回不含信任元数据的草稿；`scoring_source` 与 `review_status` 必须由服务端赋值并持久化，模型不得声明人工复核来源。任何回答仍使用未复核的确定性规则评分，或 live 评分尚未完成时，整场招聘建议必须强制为“证据不足”。升级前的历史规则评分必须在状态反序列化时迁移为待复核。
- 候选人端和面试官端必须提供人工复核入口：可修改四维评分、选择关联 Evidence 的正向/中性/负向分类并写备注；提交后必须标记为 `human/reviewed`、使旧最终报告失效，并保证迟到的后台 AI 评分无法覆盖人工结果。
- 面试官备注中的“负面证据”只能来自人工明确标记为 negative 的持久化 Evidence，必须原样绑定 signal 和 Evidence ID；缺少、尚未证明或模型推测只能归类为“仍待核验”，不能通过字符串前缀或关键词推断负面属性。
- 招聘建议理由必须由最终校准后的 recommendation、总分和置信度阈值确定性生成，不得直接采用模型自由文本；标题为“证据不足”时，正文禁止残留 `lean_no_hire`、录用或不录用结论。
- 结构化评分与状态生成使用低温度；对 llama.cpp 托管的 `gpt-oss` 必须通过 `chat_template_kwargs.reasoning_effort=low` 设置低推理强度，不能使用会被服务忽略的顶层字段，确保有限输出预算优先产生可校验的最终 JSON。
- 结构化调用必须以 temperature=0 请求 Pydantic 派生的 JSON Schema；若 Provider 明确不支持 `response_format`，允许记忆能力并降级为 Prompt 约束。首次校验失败后的唯一一次重试必须携带脱敏的字段位置/错误类型，不得重复完全相同的请求，也不得附带模型原文。
- OpenAI 兼容模型端点返回 HTTP 429/5xx、连接失败、超时，或返回成功状态但缺失可用 `choices.message.content` 时，传输层必须进行一次有界重试；再次失败只能返回脱敏降级标记，不得让 `KeyError`、原始响应体或内部地址进入业务工作流和日志。
- 模型不生成可直接使用的完整“优化回答”，只生成评分及最多三条反馈/信号。系统用确定性 STAR 框架原样保留候选人回答并显示待补充占位符，避免模型新增姓名、会议、工具、日期、比例、人数、金额或业务结果；兼容旧输出时仍必须拒绝原回答不存在的数值。
- 服务停止时必须先取消并等待后台评分/补题任务，再去重关闭文本、简历、ASR 和全模态客户端；单个关闭失败不得阻断其他资源释放。

### 6.4 隐私与安全

- 开始监听前必须获得明确确认，并持续显示录音/转写状态。
- 默认本地处理；在候选人知情同意后，全场录音默认保存到本机会话目录（`data/recordings/{session_id}.wav`），仅当前账号可见，可在结束后下载或删除；保存期限按单场会话配置。
- 同一会话只保留状态中记录的当前录音；页面退出补存 WebM/M4A 替换 WAV 后，下载必须以持久化文件名为准，删除被取代的编码副本，并返回与实际编码匹配的媒体类型。
- API Key、简历敏感字段和逐字稿不得出现在 Debug Console。
- Agent 运行日志只允许记录路由、输入长度、耗时和异常类型等元数据，不得记录 Prompt、简历、逐字稿、模型响应正文或原始异常文本。
- 本地模型连接失败、超时或 HTTP 5xx 必须先在传输层有限重试，不能伪装成模型正文并占用结构化 JSON 修复次数；最终错误只暴露异常类型和脱敏阶段，不得包含 Provider 响应正文或地址细节。
- 自动驾驶必须把用户的公开检索授权完整传递到公司和面试官子工作流；未授权时不得调用搜索 Provider，已授权时不得在子流程中静默降级为未授权。
- 事实卡只能从有实质语义的来源摘要生成；图片描述、导航文案和单独页面标题只作为原始来源展示，不能因来自官网就自动成为“已验证事实”。人物与公司联合检索时，任一明确引用实体匹配的官方域均应保留官方来源标识。
- 上传或重新解析同一候选人的简历时，必须保留会话显示姓名；只有简历中的明确姓名或用户修改才能覆盖它，模型缺失身份字段不得把会话降级为“未命名”。
- 后台任务异常只记录异常类型与脱敏阶段，不得把可能夹带简历、转写或 Provider 信息的原始异常文本写入日志或 Debug 事件。
- Debug 事件查询必须先按当前账号、会话和级别过滤，再应用 `limit`；其他账号的高频事件不得挤占当前账号的返回名额。
- 账号名唯一性以数据库约束为最终依据；并发注册冲突必须稳定返回 409，不得暴露为数据库 500 错误。
- 导出、删除和保留策略必须以单场会话为边界。
- 单场会话只能对应一个候选人证据边界：尚无真实回答/转写/证据/录音时，更换简历必须统一失效旧策略、题目和报告；已有上述活动后禁止覆盖简历或重新生成候选人方案，要求新建会话，避免静默删除或混合候选人数据。上传新简历必须在文档解析和可选 LLM 结构化之前快速预检，并在写入时再次检查，避免无效模型调用与并发覆盖。

## 7. 建议的数据边界

- `LiveInterviewSession`：状态、轮次、开始/结束时间、连接游标、隐私设置、滚动摘要、摘要覆盖游标、重复片段计数、能力覆盖引导、蓝图问题使用图、全场录音文件名/大小/保存时间（`audio_file`/`audio_size_bytes`/`audio_saved_at`）。
- `TranscriptSegment`：顺序号、时间戳、说话人、文本、稳定性和确认状态。
- `ConversationTurn`：问题、回答、关联片段和能力维度。
- `QuestionSuggestion`：结构化建议、理由、证据缺口、状态和用户操作。
- `LiveInterviewRecord`：确认后的问答和评价，继续复用现有证据模型。

这些模型与最终 `InterviewState` 关联，但实时片段应独立持久化，避免每个音频块重写整个会话 JSON。

## 9. 验收标准

- 面试官可以从 UI 开始和结束一场实时会话。
- 每个稳定候选人回答最多触发一次新的问题规划。
- 建议问题明确绑定岗位能力、现有问题和证据缺口。
- 面试官可以采用、编辑、跳过建议，系统保存该决定。
- LLM 或 ASR 故障不会丢失已经确认的转写。
- 只有确认后的候选人回答进入 `live_interview` 证据。
- 连续分段转写中无法确认说话人的片段必须进入审阅队列，不得自动进入证据。
- 断线重连不会重复生成回答、证据或建议。
- 真实模型下 Live 动作卡 E2E 脚本必须通过；建议延迟目标未满足时，Debug Console 和脚本耗时必须能解释慢在哪里。
- 搜索到疑似实体纠错时，用户能接受或拒绝，系统不得自动更名。
- 标题型 JD 会触发补充提示，生成内容清晰标记哪些是明确要求、哪些是 AI 推测。
- 简历待确认项完成处理前，不得进入最终报告的事实依据。

## 10. 本阶段不做

- AI 自动替代面试官开口提问或控制会议软件。
- 未经明确同意的后台录音。
- 根据声音、口音、表情、年龄、性别等敏感特征进行招聘判断。
- 在证据门槛不足时自动给出录用或淘汰结论。
- 第一版同时支持所有会议平台插件；先完成浏览器内本地工作台。
