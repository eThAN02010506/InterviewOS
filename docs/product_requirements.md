# InterviewOS 产品需求文档

## 1. 产品目标

InterviewOS 是一个面向候选人和面试官的本地优先面试智能系统。系统在面试前理解
候选人、岗位、公司和面试官，在面试中辅助提问和记录证据，在面试后生成可追溯的
评价与改进建议。

最终目标是让 AI 接管面试流程中的低价值操作：资料整理、事实校验、问题准备、追问
建议、转写记录、证据归档、评分汇总和报告生成。AI 不接管候选人的真实回答，也不
绕过面试官对提问、事实修正、证据确认和录用建议的最终判断。

当前阶段的重点是实现 **面试官实时 Copilot**：在获得明确授权后监听面试对话，持续
整理候选人的回答和能力信号，并在不打断交流的前提下为面试官准备下一道问题。

本文档是实现过程中的产品真实来源之一。每次完成一批重要功能时，应同步更新本文件
和 `README.md`，再提交包含充分说明的 commit。文档需要记录：当前已完成能力、下一步
顺序、已知限制、隐私/安全边界，以及真实测试结论。

## 1.1 产品原则

- 本地优先：简历、转写、密钥和调试信息默认保留在本机或用户明确配置的局域网服务中。
- 证据优先：报告、评分和招聘建议必须绑定可追溯证据；证据不足时系统应说明不足，而不是编造结论。
- 人类确认：实体纠错、简历争议项、公开搜索推断和最终招聘判断必须保留用户确认流程。
- 现场可用：面试中 UI 要快、安静、可扫读，不能因为 AI 建议打断面试节奏。
- 可观测但脱敏：Debug Console 应解释耗时、重试和降级路径，但不能泄漏 API Key、简历隐私或完整逐字稿。

## 2. 用户与场景

### 2.1 面试官

- 面试前查看结构化面试计划、能力维度和建议问题。
- 面试中查看实时转写、已覆盖信号、待验证信号和下一问题建议。
- 面试官始终决定是否采用、修改、跳过或延后 AI 建议。
- 面试后审阅记录、纠正说话人或转写错误，再生成评价报告。

### 2.2 候选人

- 面试前获得岗位和面试官分析、准备策略及模拟面试。
- 仅在知情和同意的情况下参与被录音或转写的真实面试。
- 面试记录与招聘判断不得混入未确认的简历事实或公开搜索推测。

## 3. 当前实现状态

### 3.1 已完成

- 候选人端和面试官端分离的基础 UI。
- PDF 与 Word `.docx` 简历上传、解析、警告和人工审阅项识别。
- 候选人、岗位、公司、面试官分析，以及候选人准备策略和企业面试设计。
- Tavily、SearXNG、Brave 搜索 Provider 接入，运行时配置和本地持久化。
- 实体确认机制：例如搜索到“芯视界”时，可以保留“芯世界”为用户输入，等待用户确认是否更正；用户也可以手动编辑确认后的 canonical name。
- 搜索事实卡片：结论绑定来源，并区分已验证、推测、冲突、已确认或已排除；UI 按冲突、公司、面试官、技术方向和公开观点分组展示，展示来源数量、最佳来源质量、抓取时间、缓存命中状态、筛选原因和生成时间，并支持确认使用、排除和恢复待审。
- 简历真实性审阅闭环：已支持确认、修改、要求材料、忽略，并可让后续 Agent 使用确认后的候选人事实上下文。
- JD 完整性审阅闭环：标题型或不完整 JD 会区分明确要求与 AI 推测，推测要求可确认、编辑为明确要求或删除。
- Mock 面试闭环：候选人回答、追问、评分、证据记录、最终报告和改进建议。
- Debug Console：展示 Agent 生命周期、耗时、故障、设置状态和连接探针，并进行密钥脱敏。
- Live Interview Copilot 的轮次式 MVP：面试官明确确认后，支持手动文本或单轮录音转写，生成下一问题建议，并允许采用、编辑或跳过。
- Live evidence 审阅闭环：转写片段可在归档前修改说话人与文本，候选人回答可确认为 `live_interview` 证据，批量审阅队列会提示证据数量和胜任力覆盖是否达到招聘评价门槛；已归档 live 证据可撤销，转写片段保留以便修正后重新确认；多个候选人片段可合并为一个回答再评分；已归档记录可在保留证据链的前提下重评。
- 连续分段监听 MVP：浏览器按短音频块录制并顺序上传到现有 HTTP ASR，展示队列/转写状态，默认把分段标记为 `unknown` 说话人，必须审阅后才能形成证据。
- 面试官端真实测试：已通过本地 API 跑通企业面试设计、live 记录、证据归档和最终评价；证据不足与证据充分两条路径均有回归测试。
- ASR/LLM 局域网联调：
  - 文本推理模型：`http://192.168.1.97:8001`，`gpt-oss-20b`。
  - 默认 ASR：`http://192.168.1.97:8003`，MiMo-V2.5-ASR，已验证可返回完整多句转写。
  - 备选 ASR：`http://192.168.1.8:9001`，接口可用且更快，但实测同一多句音频只返回首句，因此暂不作为默认证据来源。

- 简历真实性增强：要求材料后的材料收集、附件绑定和复核提醒仍需完善。
- 现场转写证据增强：确认后撤销、多片段合并为一个回答、保留证据链重评已完成；自动回答边界检测仍需完善。

- 长面试性能和可靠性：60-90 分钟压力测试、Token/成本统计、缓存和并发优化。

## 4. 实时面试 Copilot 核心流程

1. 面试官选择候选人会话和面试轮次。
2. UI 显示麦克风、转写和数据用途说明，由面试官确认候选人已知情。
3. 面试官点击“开始监听”，浏览器采集音频并分片发送到本地服务。
4. ASR 返回带时间戳的增量转写；用户可暂停、恢复和手动修正文本。
5. 系统区分面试官问题与候选人回答。无法可靠判断时标记为“待确认”，不得直接形成证据。
6. 候选人回答结束后，系统更新能力覆盖和缺失信号，并准备下一问题建议。
7. 面试官选择“采用”“编辑后采用”“跳过”或自行提问。
8. 面试结束后，面试官审阅记录并确认，系统再运行最终招聘评价。

## 5. 功能需求

### FR-1 实时会话控制

- 支持开始、暂停、恢复和结束实时面试。
- 同一面试会话只允许一个活动监听流，重复连接不得产生重复证据。
- 浏览器断线后可以从最后确认的转写片段恢复。
- UI 必须持续显示监听状态，不允许后台静默录音。

### FR-2 增量转写

- 阶段一允许浏览器以短音频块顺序上传到现有 HTTP ASR 文件转写接口，作为连续监听的
  最小可用版本。该版本必须清晰标注“分段转写”，不伪装成真正的实时流式 ASR。
- 阶段二浏览器以短音频块发送数据，服务端维护长生命周期 ASR 实例，禁止每块重新加载模型。
- ASR 通过可配置的局域网 Provider 接入。已验证的默认地址为
  `http://192.168.1.97:8003`（MiMo-V2.5-ASR），不得硬编码到业务逻辑；用户可以在设置界面修改地址、
  模型名、请求超时和鉴权信息。
- 接入适配器同时覆盖健康检查、批量转写和流式转写能力探测。若服务只支持文件上传，
  后端应合并短音频块后异步提交，不让该协议差异进入前端代码。
- 转写片段包含 ID、开始时间、结束时间、文本、稳定状态和说话人角色。
- 临时文本可被后续 ASR 修订；只有稳定片段可以进入问题规划上下文。
- 支持面试官手动粘贴文本，便于无麦克风环境测试同一数据流。
- 当前 HTTP 轮次式录音上传已经完成；短音频块连续上传应复用该 API 边界，后续真正流式
  监听不得改变前端对 ASR Provider 的抽象边界。
- 在没有可靠 diarization 之前，连续分段转写默认说话人为“待确认/unknown”，用户修正
  说话人和文本后才能进入证据确认流程。

### FR-3 说话人和轮次识别

- 最低可用版本允许用户手动指定“面试官/候选人”。
- 自动说话人识别属于增强能力，低置信度结果必须请求确认。
- 一个问答轮次由面试官问题、候选人回答和可选追问组成。
- 寒暄、隐私信息和未完成语句不进入能力评价。

### FR-4 下一问题规划

系统在候选人完成回答后生成结构化建议，至少包含：

- `suggested_question`：建议问题；
- `question_type`：追问、下一主问题或澄清；
- `competency`：要验证的岗位能力；
- `rationale`：为什么现在问；
- `evidence_gap`：当前缺失的证据；
- `expected_signals`：回答中应观察的信号；
- `source_question_id`：来源于哪道计划问题；
- `confidence`：建议可信度；
- `alternatives`：最多两个备选问题。

规划优先级为：

1. 当前回答暴露了关键缺口时，提出一次证据型追问；
2. 当前能力证据已经充分时，推进到尚未覆盖的岗位能力；
3. 回答或转写不完整时，只建议澄清，不进行负面评价；
4. 所有核心能力已覆盖时，建议结束该轮或让候选人提问。

AI 不得连续生成无限追问。默认每道主问题最多两次追问，面试官可以调整上限。

### FR-5 实时面试官工作台

页面采用三栏或主次双栏布局：

- 当前对话：实时转写、说话人、时间戳和修正入口；
- 面试地图：计划问题、能力覆盖、已确认信号和待验证项；
- Copilot：下一问题、提问理由、预期信号和备选问题。

关键操作必须在单击内完成：采用、编辑、跳过、固定问题、标记已问、暂停 AI 建议。
建议卡不得遮挡对话，也不应自动朗读或自动向候选人提问。
连续监听模式必须始终显示录音状态、待上传片段数、正在转写状态和降级提示；停止监听
后仍需完成队列内已录到片段的处理，失败片段不得阻塞用户手动录入。

### FR-6 证据与评价

- 实时片段本身不是招聘证据；只有完整候选人回答经确认或稳定处理后才能形成证据。
- 每条证据绑定问答轮次、能力维度、原始转写片段和来源 `live_interview`。
- AI 推断与候选人原话必须分开存储和展示。
- 说话人未确认、转写不稳定或上下文不足时，证据状态为“待确认”。
- 最终评价继续遵守现有证据门槛和来源约束。

### FR-7 调试与运行指标

Debug Console 增加以下脱敏事件：

- 音频块数量和处理延迟，不记录原始音频内容；
- ASR 实时系数、转写失败和断线恢复；
- 问题规划触发原因、模型耗时、重试和降级路径；
- 建议被采用、编辑或跳过的结果；
- 上下文字符数、Token 和成本估算。

### FR-8 实体确认

- 当搜索结果显示用户输入实体可能是别名、错字或同名混淆时，系统必须创建确认项。
- UI 应明确显示“是否将 A 更正为 B”，并展示支持来源。
- 用户确认前，系统不得把候选实体改写为 canonical identity。
- 用户可以接受、更正为其他名称、拒绝或暂缓；每个决定都应记录到会话状态。

### FR-9 JD 完整性校验

- 系统应判断 JD 是否只有标题、职责不足、要求不足或缺少团队背景。
- 上下文不足时，问题生成仍可继续，但必须标记为“通用问题”或“AI 推测”。
- UI 应提示补充岗位职责、任职要求、团队规模、技术栈、业务目标和面试轮次目标。
- 面试计划中必须区分用户明确给出的要求和 AI 根据岗位标题推测的要求。

### FR-10 事实卡片

- 搜索结论应按公司、面试官、技术方向、公开观点、争议信息分组。
- 每条事实卡包含结论、状态、来源 URL、来源数量、最佳来源质量、真实抓取时间、缓存命中状态、筛选原因、事实卡生成时间和可信度说明。
- 冲突信息不得被合并成单一结论；需要在 UI 中并列展示并请求用户判断。
- 事实卡只能用于增强上下文，不能替代候选人的面试表现证据。

### FR-11 简历真实性审阅

- 每个简历待确认项支持确认、修改、要求材料、忽略。
- 修改后的事实应保留原文和修订后的结构化值。
- “要求材料”项应进入候选人准备建议和面试官核验清单。
- 后续 Agent 只能读取确认、修改后确认或明确允许使用的事实。

## 6. 非功能需求

### 6.1 延迟

- 稳定转写应在说话后 2 秒内出现，目标值为 1 秒内。
- 回答结束后的第一张建议卡应在 5 秒内出现。
- UI 更新不得等待最终评价 Agent；实时辅助和面试后评价使用不同任务队列。

### 6.2 上下文与性能

- 不把整场逐字稿反复发送给模型。
- 模型上下文由最近若干轮对话、滚动摘要、岗位能力地图和已确认信号组成。
- 增量处理复杂度应接近 O(n)，其中 n 为转写片段数量。
- 每场面试设置最大时长、片段数和上下文 Token 上限。

### 6.3 可用性与降级

- LLM 不可用时继续转写和手动记录问题。
- ASR 不可用时允许粘贴文本或手动录入问答。
- ASR 健康检查失败时禁止显示“正在监听”，UI 应明确显示“音频采集中但转写服务不可用”
  或“未开始采集”，避免给用户错误的隐私和运行状态暗示。
- 网络或浏览器断开时保留已确认片段，恢复后不得重复评分。
- 模型返回无效结构时展示基于面试计划的确定性备选问题。

### 6.4 隐私与安全

- 开始监听前必须获得明确确认，并持续显示录音/转写状态。
- 默认本地处理；是否保存原始音频与保存期限由用户配置，默认不保存原始音频。
- API Key、简历敏感字段和逐字稿不得出现在 Debug Console。
- 导出、删除和保留策略必须以单场会话为边界。

## 7. 建议的数据边界

- `LiveInterviewSession`：状态、轮次、开始/结束时间、连接游标和隐私设置。
- `TranscriptSegment`：顺序号、时间戳、说话人、文本、稳定性和确认状态。
- `ConversationTurn`：问题、回答、关联片段和能力维度。
- `QuestionSuggestion`：结构化建议、理由、证据缺口、状态和用户操作。
- `LiveInterviewRecord`：确认后的问答和评价，继续复用现有证据模型。

这些模型与最终 `InterviewState` 关联，但实时片段应独立持久化，避免每个音频块重写整个会话 JSON。

## 9. 验收标准

- 面试官可以从 UI 开始和结束一场实时会话。
- 每个稳定候选人回答最多触发一次新的问题规划。
- 建议问题明确绑定岗位能力、现有问题和证据缺口。
- 面试官可以采用、编辑、跳过建议，系统保存该决定。
- LLM 或 ASR 故障不会丢失已经确认的转写。
- 只有确认后的候选人回答进入 `live_interview` 证据。
- 连续分段转写中无法确认说话人的片段必须进入审阅队列，不得自动进入证据。
- 断线重连不会重复生成回答、证据或建议。
- 真实模型下建议延迟满足目标，Debug Console 可以解释慢在哪里。
- 搜索到疑似实体纠错时，用户能接受或拒绝，系统不得自动更名。
- 标题型 JD 会触发补充提示，生成内容清晰标记哪些是明确要求、哪些是 AI 推测。
- 简历待确认项完成处理前，不得进入最终报告的事实依据。

## 10. 本阶段不做

- AI 自动替代面试官开口提问或控制会议软件。
- 未经明确同意的后台录音。
- 根据声音、口音、表情、年龄、性别等敏感特征进行招聘判断。
- 在证据门槛不足时自动给出录用或淘汰结论。
- 第一版同时支持所有会议平台插件；先完成浏览器内本地工作台。
